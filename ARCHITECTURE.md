# Architecture

Riftbound Practice Table is an unofficial Riftbound practice app. Official Origins/Proving Grounds metadata and artwork come from Riot's public gallery; seven retail starter lists live in `packages/riftbound-content`. The original Ember Concord content remains as a legacy prototype.

The TypeScript practice engine consumes typed actions and exposes per-player projections. The server owns shuffling, authentication, rooms and sequencing; clients never submit match state. Socket.IO connects the React/Electron renderer to the server. Electron uses a sandboxed renderer. Practice sessions and private duel matches persist as validated atomic JSON snapshots. Bearer resume tokens are hashed at rest; sockets bind to a token or lobby member and disconnecting removes only that live binding. Restarts restore the full engine state, including unresolved choices. Account sessions remain in memory.

Packages: shared (protocol), game-content (original cards), game-rules (module contract), game-engine (transitions), ui (shared presentation). Apps: server and desktop. Tests cover engine and independent network clients. Distribution uses electron-builder and native Windows/macOS runners.

Hidden hands and deck order must be removed before publication. Session tokens are bearer secrets. Match actions require an expected revision to prevent replays. Deployment requires private Tailscale access or a TLS reverse proxy.

Accounts, email addresses, owned-card counts and account-owned decks are stored by the server in SQLite using sql.js, with serialized writes and atomic snapshot replacement. Registration requires a unique normalized email and a password of 6–128 characters; older databases receive a non-destructive email-column migration. Collection mutations validate known non-token card IDs and integer quantities, and scope every query to the authenticated owner. Profile and collection writes roll back on persistence failure. Passwords use salted scrypt hashes; expiring account sessions remain in server memory. The desktop editor authenticates over Socket.IO and saves decks through owner-scoped queries. Lobby reconnect tokens are separate from account tokens. Local SQLite deck IPC has been superseded by server-owned deck storage so friends can sign in from different computers.

Renderer entry: `apps/desktop/src/entry.tsx`. `App.tsx` separates Play, My decks, My cards, Account, With friends and settings. `GameTable.tsx` displays artwork, hidden opponent hands, bases, battlefields, runes, scoring and inspection. Card selection, highlighted targets and destinations emit server-provided legal actions with the current revision. `CardArt.tsx` provides reusable artwork/fallbacks; `RiftboundDecks.tsx` supplies account state, profile forms and a separate editor view; `DeckLibrary.tsx` supplies saved-deck tiles, collection progress, searching, domain filtering and starter templates; `Collection.tsx` tracks owned counts. A shared mounted account/editor component keeps navigation state synchronized, with per-server session tokens in sessionStorage for tab refresh/reconnect. Email delivery and verification are deferred. Responsive styles are in `table.css`.

`useCardDrag.ts` handles mouse/touch Pointer Events with capture, a movement threshold, Escape/cancel cleanup, revision checks and source-click suppression after dragging. `card-drops.ts` resolves destinations solely against the latest legal server actions. Untargeted cards drop into base; targeted spells drop onto units, with a second-target choice when needed. Ready units drop onto legal locations. Shift-drop chooses a legal Accelerate action. `card-drag.css` provides a noninteractive cursor preview, dimmed source and destination highlights. Existing click and keyboard flows remain available.

Practice AI reads a projection without the opponent's hand/deck order and uses a bounded action loop. Supported mechanics include optional Accelerate payments, Lee Sin/Viktor legend abilities, Lux spell-only energy, once-per-battlefield scoring and final-point restrictions. Interactive mode adds a priority-controlled, last-in-first-out spell/ability chain, showdown windows, simultaneous combat with validated Tank/Backline damage ordering, group movement, discard/retrieve tasks and selected further abilities/triggers. New and resumed server matches always use interactive rules; older snapshots are upgraded on load. Hidden cards, equipment, full trigger ordering and many card effects remain unsupported and disclosed in the UI. Server diagnostics are sanitized JSONL at `.runtime/logs/server.jsonl`; failures return request IDs. Chrome browser tests use isolated accounts and server ports.

The engine publishes a bounded, monotonically numbered event stream for plays, movement, combat damage, defeat, abilities, scoring, draws and rune channeling. Per-viewer projections strip opponent draw card IDs and instance IDs; own draw identities support face-up animations. `BattleEffects.tsx` consumes only new events, scoped by match UUID; refreshes do not replay them. `CardFlights.tsx` reads visible deck/hand/base/field anchors and retains hand positions after played cards leave the DOM. Noninteractive overlays animate draws and plays; `RuneIcon.tsx` supplies six SVG domain glyphs and the custom card-back sigil. `table-cinematic.css` provides gem runes, card flights and reduced-motion alternatives.

The server chooses the first player using crypto randomness and assigns a unique match ID. `OpeningFlip.tsx` displays that authoritative result, traps keyboard focus and permits skipping. Initial events wait until the reveal finishes. Duel setup deals four cards to both players; the first player channels two runes and draws on turn one. The second player channels three runes on their first turn, then both channel two normally. AI-first starts run the bounded bot loop before returning the player's turn. Chrome test servers inject each starting position only under NODE_ENV=test.

Legend readiness, temporary restricted spell energy and scored battlefields are authoritative server state. Rules source: Riot's October 9, 2026 Core Rules, https://cmsassets.rgpub.io/sanity/files/dsfx7636/news_live/5c7946f7c3b8c6e0faff85ab6dadc6d2e721ea94.pdf (duel 487, scoring 471–474, Accelerate 805, resource pools 167).

`practice-protocol.ts` defines the validated action protocol shared by practice and friend matches. `practiceActor` identifies the player responsible for priority or a mandatory task independently of the active turn. `MatchControls.tsx` displays chains, tasks and damage ordering; `GroupMovement` builds a validated group action from individual legal destinations. `match-view.ts` normalizes a private per-player projection so each table places its owner at index zero without exposing hidden state. The server always determines the actual acting player from the lobby session.

`Snapshots` writes validated versioned snapshots with owner-only file permissions and atomic replacement. Practice saves before committing state; lobby match actions roll back in-memory state if persistence fails. `MATCHES_DIR` selects the snapshot directory; custom account files isolate snapshot storage by default. Lobby passwords are stored as scrypt hashes and bearer tokens as SHA-256 hashes. Sessions currently have no snapshot retention policy; operational cleanup and cross-process snapshot sharing remain future work. Run one server per snapshot directory.
